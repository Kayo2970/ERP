## Overview

LEADS ERP (`leads-dashboard`) is an enterprise resource planning and student activity operations platform built on Next.js 16 (App Router) and React 19. It manages departmental members, role hierarchies, committees, events, event passes, budgets, procurement, reimbursements, task assignments, performance ratings, form builders with public landing pages, digital visiting cards with Apple/Google Wallet integration, announcements, and automated email workflows.

The system uses an embedded, zero-dependency, encrypted flat-file database layer (`data/*.json` with per-collection async mutexes and AES-GCM encryption), avoiding external database hosting while maintaining transactional integrity.

### 2. Authentication & Authorization (`src/lib/permissions.ts`, `src/lib/permissions-server.ts`)
- **Location:** `leads-dashboard/src/lib/permissions*.ts`, `session.ts`, `password.ts`, `member-guard.ts`
- **Pattern:** Stateless client token + server-side session hashing (SHA-256) combined with 7-tier hierarchical Role-Based Access Control (RBAC):
  - **Tier 1:** Super User (System Administrators, full read/write/override access)
  - **Tier 2:** Centre Head / President / Core Leadership
  - **Tier 3:** Department Heads (Lead Members)
  - **Tier 4:** Advisory Board / Faculty Advisors
  - **Tier 5:** Core Committee Members
  - **Tier 6:** Training Associates
  - **Tier 7:** Alumni / Guest accounts
- **Security:**
  - Password hashing via Node built-in `crypto.scryptSync` with unique 16-byte salts and `timingSafeEqual`.
  - Sensitive files encrypted with AES-GCM; database files never committed to git.
  - Server endpoints enforce strict tier checks and session revocation verification.

## Technical Debt & Architectural Watchpoints

- [ ] **In-Process Schedulers:** Schedulers run in-process via `instrumentation.ts`. If multiple PM2 cluster workers run, tasks could double-trigger without shared lock mechanism (currently guarded by idempotency rows like `birthdayEmailLog`).
- [ ] **In-Memory Collection Filtering:** File-based JSON read-modify-write requires parsing the full collection array into Node memory. Sufficient for ~10,000s of records, but will require indexing or SQLite/Postgres migration if volume grows by orders of magnitude.
- [ ] **Live Pass Updates (`card-wallet-pass.ts`):** WalletWallet PUT response limitations currently create a new pass serial on card updates rather than in-place push (`ponytail:` noted).
- [ ] **Automated Test Suite:** Acceptance verification currently relies on `npx tsc --noEmit` and `npm run build`. Adding a fast unit test runner (e.g. Node test runner or Vitest) for core permissions and DB mutexes would provide additional regression defense.

## Conventions & Standards

- **Coding Standard:** TypeScript Strict mode, ESLint with `eslint-config-next`.
- **Database Access:** Never read/write `data/*.json` directly; always use `readCollection()` and `mutateCollection()` from `src/lib/server-db.ts`.
- **Authorization:** Every API route verifies caller identity and role using `getAuthenticatedMember(req)` or `verifyPermission()`.
- **Deployment Requirement:** As stated in `CLAUDE.md`, all changes must pass `npx tsc --noEmit` and `npm run build` before pushing to `main`.
